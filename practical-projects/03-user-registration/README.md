This is the third project in **Phase 10: Practical Projects**. It focuses on identity-like data validation, canonical values, duplicate prevention, indexed lookup, safe updates, explicit account states, and service-layer boundaries without introducing real authentication or personal data.

**Estimated study and implementation time:** 180–240 minutes.

## Learning goals

By the end of this project, you should be able to:

- turn identity-like input rules into explicit validation functions;
- distinguish display data from canonical identifiers;
- normalize Unicode and whitespace intentionally;
- prevent duplicates after normalization rather than before it;
- maintain multiple lookup indexes without exposing internal dictionaries;
- update indexed fields without leaving stale keys behind;
- model account lifecycle states with an enum and explicit transitions;
- separate immutable user snapshots from a mutable registry service;
- test mutation safety, lookup behavior, boundary cases, and invalid transitions.

## 1. Project brief

Build an in-memory user registry that can:

1. register fictional users;
2. assign sequential positive user IDs;
3. normalize full names, usernames, and email identifiers;
4. prevent duplicate usernames and emails after canonicalization;
5. look users up by ID, username, or email;
6. search across identity fields;
7. update name, username, and email safely;
8. keep username and email indexes synchronized after updates;
9. suspend, reactivate, or deactivate users under explicit state rules;
10. prove success and failure behavior with automated tests.

## 2. Data contract

Each user contains:

```text
user_id   -> positive integer generated by the registry
full_name -> non-blank normalized text, at most 80 characters
username  -> canonical 3–30 character identifier
email     -> canonical email identifier under this project's rules
status    -> active, suspended, or deactivated
```

The project uses only fictional demonstration data.

## 3. Why canonical values matter

These inputs should represent the same username:

```text
Maya.Chen
maya.chen
  MAYA.CHEN  
```

If uniqueness is checked before normalization, equivalent values can slip into the registry as separate accounts.

`normalize_username(...)` therefore converts the input to one canonical representation before lookup or duplicate checks.

## 4. Unicode normalization

The project uses Unicode **NFKC** normalization before validating identity-like text.

For example, full-width characters such as:

```text
ＡＢＣ
```

normalize to:

```text
ABC
```

NFKC is an application design decision here. Unicode normalization changes representation, so production systems should choose a normalization policy deliberately for their own identity requirements.

## 5. Full-name normalization

Full names preserve readable casing but normalize whitespace:

```python
normalize_full_name("  Maya   Chen  ")
# "Maya Chen"
```

The function rejects blank values and names longer than the project limit.

A full name is display-oriented data. It is not used as a unique account key.

## 6. Username contract

Usernames are:

- normalized with NFKC;
- trimmed;
- converted with `casefold()`;
- limited to 3–30 ASCII characters;
- required to begin with a letter or digit;
- allowed to contain letters, digits, `.`, `_`, and `-`.

Examples:

```text
Maya.Chen -> maya.chen
NOAH-R    -> noah-r
```

These are project rules, not universal username rules.

## 7. Email contract

This project intentionally implements a **restricted application-level email identifier policy**, not a complete RFC email parser.

The registry:

- trims surrounding whitespace;
- applies NFKC and `casefold()`;
- requires exactly one `@`;
- rejects whitespace inside the address;
- validates a restricted ASCII local-part character set;
- rejects leading, trailing, and repeated dots in the local part;
- converts Unicode domains with Python's IDNA codec;
- requires a dot-separated domain with valid labels;
- enforces project length limits.

Example:

```python
normalize_email("MAYA@Example.COM")
# "maya@example.com"
```

And a Unicode domain can become an ASCII IDNA form:

```python
normalize_email("user@bücher.example")
# "user@xn--bcher-kva.example"
```

The project treats the full canonical email value as case-insensitive for uniqueness. Real systems may need different requirements, especially for interoperability and standards compliance.

## 8. The immutable `User` model

`User` is a frozen dataclass:

```python
@dataclass(frozen=True, slots=True)
class User:
    user_id: int
    full_name: str
    username: str
    email: str
    status: UserStatus = UserStatus.ACTIVE
```

Validation also runs when the dataclass constructor is called directly.

The registry never mutates an existing `User` object. Changes create a replacement snapshot.

## 9. Registry service boundaries

`UserRegistry` owns mutable collection behavior:

```text
register
lookup
search
change indexed identity fields
change display name
state transitions
```

The `User` model describes one valid snapshot. The registry coordinates relationships between multiple users.

That separation prevents global uniqueness rules from being hidden inside an isolated record object that cannot see the rest of the collection.

## 10. Sequential IDs without gaps from rejected registrations

`register(...)` builds and validates a candidate before mutating registry state.

If the username or email is already taken, the registration fails and the next ID is **not** consumed.

```text
successful user -> ID 1
rejected duplicate -> no ID consumed
next successful user -> ID 2
```

This behavior is a project convention designed to make mutation order visible and testable.

## 11. Duplicate prevention

The registry keeps canonical indexes for:

```text
username -> user_id
email    -> user_id
```

So these registrations collide:

```text
maya.chen
MAYA.CHEN
```

And these email identifiers collide under this project's policy:

```text
maya@example.com
MAYA@EXAMPLE.COM
```

A duplicate raises `DuplicateUserError` before registry state changes.

## 12. Indexed lookup

The registry supports:

```python
registry.get_by_id(1)
registry.get_by_username("MAYA.CHEN")
registry.get_by_email("maya@EXAMPLE.COM")
```

Lookup inputs go through the same canonicalization functions used during registration.

Missing values raise `UserNotFoundError` instead of leaking a raw dictionary `KeyError`.

## 13. Search behavior

`search(...)` performs a case-insensitive substring search over:

- full name;
- canonical username;
- canonical email.

Results preserve registration order.

An optional `UserStatus` filter can narrow the result set.

```python
registry.search("example", status=UserStatus.ACTIVE)
```

This is a simple in-memory learning implementation, not a search-engine design.

## 14. Updating indexed fields safely

Changing a username or email has two responsibilities:

1. validate and verify the new value is available;
2. replace the old index key with the new one.

The project validates first, then mutates indexes.

A rejected duplicate update therefore leaves the original lookup key working.

## 15. Account lifecycle

The supported states are:

```text
active
suspended
deactivated
```

Allowed transitions are:

```text
active    -> suspended
suspended -> active
active    -> deactivated
suspended -> deactivated
```

`deactivated` is terminal in this version.

Invalid transitions raise `InvalidUserTransitionError`.

## 16. Why an enum is useful

`UserStatus` is an enum rather than arbitrary text.

That prevents states such as:

```text
"actve"
"paused-ish"
"disabled maybe"
```

from silently entering the model.

Enums are useful when a field has a small, explicit set of valid values.

## 20. Failure paths to inspect manually

Try:

```python
registry.register("Maya Chen", "ab", "maya@example.com")
registry.register("Maya Chen", "maya", "not-an-email")
registry.register("Other User", "MAYA", "other@example.com")
registry.get_by_id(999)
registry.reactivate(1)
```

Read the exceptions and inspect the registry after each rejected operation.

## 21. Design note: validation and uniqueness are different jobs

A username can be syntactically valid and still be unavailable because another user already owns the same canonical value.

Validation answers:

> Is this value structurally acceptable?

Uniqueness answers:

> Is this acceptable value available in this collection?

Keeping those questions separate makes the code easier to reason about and test.

## 22. Design note: indexes are derived state

The username and email dictionaries are secondary indexes derived from the canonical `User` values.

Whenever an indexed field changes, both the primary user mapping and the matching secondary index must remain consistent.

This is a small example of an invariant: several pieces of state must agree at all times.

## 23. Design note: validate before mutation

Registration and identity updates follow the same pattern:

```text
normalize -> validate -> check conflicts -> create replacement -> mutate
```

That order reduces partial-update bugs.

## 24. What this project intentionally does not include

This version does not include:

- passwords;
- password hashing;
- login sessions;
- authentication;
- authorization or roles;
- real personal data;
- email delivery or verification links;
- persistence or a database;
- external identity providers;
- a web API;
- a GUI.

Those topics introduce different security and infrastructure concerns. This project stays focused on clean in-memory domain rules.

## 25. Security note

A real registration system must not store plain-text passwords and would require substantially more security work than this educational registry provides.

Do not treat this project as a production authentication implementation.

## 30. Review checklist

Before considering your own implementation complete, verify:

- Can equivalent usernames bypass duplicate checks by changing case or spacing?
- Do email lookup and duplicate checks use the same canonicalization contract?
- Does a rejected registration leave the ID sequence unchanged?
- Do username and email updates remove stale lookup keys?
- Does a rejected update preserve the previous valid index?
- Are account states limited to explicit enum values?
- Are invalid state transitions rejected?
- Are internal dictionaries hidden from callers?
- Are passwords and real personal data intentionally absent?
- Do tests prove both success and failure paths?
